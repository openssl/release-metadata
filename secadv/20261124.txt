OpenSSL Security Advisory [24th November 2026]
==============================================

The issues listed below have been fixed in the public openssl/openssl
repository on GitHub. Releases containing these fixes are scheduled
for 1st December 2026.

Possible NULL Dereference in Non-SMTP DANE Clients (CVE-2026-84786)
===================================================================

Severity: Low

Issue summary: A DANE-enabled TLS client may crash by dereferencing a NULL
pointer when processing an unusual combination of certificate and TLSA
records.

Impact summary: The impact is limited to a client crash (potential Denial
of Service).

CWE: CWE-476: NULL Pointer Dereference

Description: A DANE-enabled TLS client that supports TLSA records with at
least one of the PKIX-TA(0) or PKIX-EE(1) usages alongside the DANE-TA(2)
usage may crash by dereferencing a NULL pointer if the server claims a trusted
CA's certificate to be its end-entity certificate and has an unusual mix of
associated TLSA records.

DANE SMTP clients should not be affected since only the
DANE-TA(2) and DANE-EE(3) TLSA record usages are specified applicable
in SMTP.  For example, the Postfix MTA is not affected, while the Exim
MTA does not at present use OpenSSL's DANE implementation.

Use of DANE in validation of RFC7250 raw public keys (RPKs) is also
unaffected, as these only use DANE-EE(3) TLSA records.

Only applications that support combining the DANE PKI with a traditional PKI
are potentially affected.  A DANE-enabled browser or similar, that uses
OpenSSL's DANE API could be affected.

FIPS impact: no
The DANE API is outside the FIPS module boundary.

OpenSSL 4.1, 4.0, 3.5, 3.0, and 1.1.1 are vulnerable to this issue.

OpenSSL 1.0.2 is not affected by this issue.

OpenSSL 4.1 users should upgrade to OpenSSL 4.1.1.
OpenSSL 4.0 users should upgrade to OpenSSL 4.0.4.
OpenSSL 3.5 users should upgrade to OpenSSL 3.5.10.

Premium support customers only:
OpenSSL 3.0 users should upgrade to OpenSSL 3.0.24.
OpenSSL 1.1.1 users should upgrade to OpenSSL 1.1.1zk.

This issue was reported on 16 September 2026 by Sanjay Rawat and on
30 October 2026 by Mohammed Alquraini (HUMAIN).
The fix has been developed by Viktor Dukhovni.

Unbounded QUIC RETIRE_CONNECTION_ID Frame Sending Queue (CVE-2026-107494)
=========================================================================

Severity: Low

Issue summary: The QUIC stack queues a RETIRE_CONNECTION_ID frame also for
retransmitted NEW_CONNECTION_ID frames. This allows a remote malicious
QUIC stack to queue an unlimited number of RETIRE_CONNECTION_ID frames.

Impact summary: A malicious remote QUIC peer can trigger an out-of-memory
condition causing a Denial of Service.

CWE: CWE-770: Allocation of Resources Without Limits or Throttling

Description: The earlier fix for CVE-2026-84784 was not complete. It
failed to ignore retransmissions of the NEW_CONNECTION_ID frame. The QUIC
implementation created and inserted a RETIRE_CONNECTION_ID frame for every
retransmitted NEW_CONNECTION_ID frame it received and there was no limit
on how many RETIRE_CONNECTION_ID frames were queued.

This issue allows a malicious remote QUIC stack to trigger an unbounded
allocation of memory and eventually an out-of-memory (OOM) condition.

FIPS impact: no
The FIPS module is not affected as the QUIC implementation is outside the
OpenSSL FIPS module boundary.

OpenSSL 4.1, 4.0, and 3.5  are vulnerable to this issue.

OpenSSL 3.0, 1.1.1 and 1.0.2 are not affected by this issue.

OpenSSL 4.1 users should upgrade to OpenSSL 4.1.1
OpenSSL 4.0 users should upgrade to OpenSSL 4.0.4
OpenSSL 3.5 users should upgrade to OpenSSL 3.5.10

This issue was reported on 29 September 2026 by moltenbit, on 16 October 2026
by Duc Anh Luu (University of Melbourne) and on 22 October 2026 by hataehoon.
The fix has been developed by Alexandr Nedvědický.

Relative CRL Distribution Point Names Rebuilt per CRL in X.509 Verification (CVE-2026-121482)
=============================================================================================

Severity: Low

Issue summary: Verifying a maliciously crafted CMS or PKCS#7 SignedData
message with CRL checking enabled may consume excessive CPU time, growing with
the square of the message size.

Impact summary: An attacker who can submit a CMS or PKCS#7 SignedData message
to an application that verifies it with CRL checking enabled can occupy a CPU
core for seconds to minutes, causing Denial of Service. Applications that
leave CRL checking disabled are not affected.

CWE: CWE-407: Inefficient Algorithmic Complexity

Description: With CRL checking enabled, OpenSSL compares each CRL distribution
point of a certificate against the issuing distribution point of every
candidate CRL. For a nameRelativeToCRLIssuer distribution point, the full name
is the CRL issuer name with the relative name appended. Since the change that
deferred this computation, crl_crldp_check() rebuilds that full name for each
candidate CRL and frees it again.

CMS_verify() and PKCS7_verify() take both the distribution points and the
candidate CRLs from the message, and this scoring runs before any signature is
checked. An application is exposed only if it sets X509_V_FLAG_CRL_CHECK on
the store and does not pass CMS_NOCRL or PKCS7_NOCRL; CRL checking is off by
default. In TLS the CRLs come from the local store, so a peer controls only
the distribution point count.

The cost grows with the product of the distribution point count, the CRL count
and the issuer name length, all chosen by the message author; a few hundred
kilobytes can occupy a CPU core for tens of seconds. Verification still fails
as it should, with no crash, no incorrect result and no memory growth.
Requiring CRL checking is what limits the severity.

FIPS impact: no
The affected code is outside the FIPS module boundary.

OpenSSL 4.1, 4.0 and 3.5 are vulnerable to this issue.

OpenSSL 3.0, 1.1.1 and 1.0.2 are not affected by this issue.

OpenSSL 4.1 users should upgrade to OpenSSL 4.1.1.
OpenSSL 4.0 users should upgrade to OpenSSL 4.0.4.
OpenSSL 3.5 users should upgrade to OpenSSL 3.5.10.

This issue was reported on 19 October 2026 by Alex Gaynor (Anthropic).
The fix has been developed by Neil Horman.
